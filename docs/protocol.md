# remote-wake protocol v1

This document is the contract between `app/` (signer), `relay/` (carrier), and
`firmware/` (verifier/executor). All three MUST implement it exactly as written.

## Identifiers & keys

- `deviceId` — 8 random bytes, lowercase hex (16 chars). Generated by firmware
  on first boot, persisted in NVS, shown during pairing.
- `deviceToken` — 32 random bytes, base64url (no padding). Generated by
  firmware on first boot. Shared with relay and phone during pairing. Gates
  relay access only; carries **no command authority**.
- Phone signing key — Ed25519. Private key lives in the phone's WebCrypto
  keystore (non-extractable). Public key (32 raw bytes, base64url) is
  registered on the device during pairing. The device stores up to 4 operator
  public keys.

## Command envelope

JSON, UTF-8. Sent phone → relay → device.

```json
{
  "v": 1,
  "dev": "a1b2c3d4e5f60718",
  "id": "f3b0…-uuid4",
  "ts": 1724457600,
  "ctr": 42,
  "act": "wake",
  "args": {},
  "kid": "p1",
  "sig": "base64url(64-byte Ed25519 signature)"
}
```

| Field  | Meaning |
|--------|---------|
| `v`    | Protocol version, integer `1`. |
| `dev`  | Target `deviceId`. |
| `id`   | UUIDv4, unique per command; echoed in responses. |
| `ts`   | Unix seconds at signing time (phone clock). |
| `ctr`  | Strictly-increasing unsigned counter per key (`kid`), starts at 1. Phone persists it; device persists high-water mark per `kid` in NVS. |
| `act`  | Action name, see table below. |
| `args` | Action arguments object (may be `{}`; never absent). |
| `kid`  | Operator key slot id (`p1`…`p4`). |
| `sig`  | Ed25519 signature, base64url, over the **signing string** below. |

### Signing string

Signatures are computed over a canonical byte string, NOT over the JSON
(avoids canonical-JSON pitfalls):

```
remote-wake-v1\n
<dev>\n
<id>\n
<ts>\n
<ctr>\n
<act>\n
<args-json>
```

`<args-json>` is the `args` object serialized with keys sorted
lexicographically, no whitespace, UTF-8 (e.g. `{}`, `{"ms":5000}`). The exact
bytes of this serialization MUST also be what is placed in the envelope's
`args` (the device re-serializes with the same rules before verifying).

### Device-side verification (all MUST pass, in order)

1. `v == 1`, `dev` matches own id.
2. `kid` refers to a registered operator key.
3. `sig` verifies over the signing string with that key.
4. `|ts - now| <= 90` seconds (device syncs via SNTP).
5. `ctr > lastCtr[kid]`; on success persist `ctr` as new high-water mark
   **before** executing the action.
6. `act` is known and enabled.

Failures produce an `err` response (below) and are rate-limited.

## Actions

| `act`        | `args`                          | Effect |
|--------------|---------------------------------|--------|
| `ping`       | `{}`                            | Liveness; responds `pong` with uptime + state. |
| `status`     | `{}`                            | Reports USB mount/suspend state, Wi-Fi RSSI, firmware version. |
| `wake`       | `{}`                            | HID: press+release a zero-side-effect key (Left-Ctrl) twice, 50 ms apart. Wakes a sleeping host. |
| `type`       | `{"text": "...", "enter": true}`| HID: type UTF-8 text (US layout mapping), optional trailing Enter. Max 256 chars. Used for typing the login password. |
| `keys`       | `{"seq": [["LGUI","L"],["ENTER"]]}` | HID: sequence of chords, each = list of key names, pressed together then released, 30 ms apart. Max 32 chords. |
| `power_tap`  | `{"ms": 200}` (50–1000)         | Drive PWR_SW optocoupler for `ms` (default 200) — power on / graceful ACPI signal. |
| `power_hold` | `{"ms": 6000}` (3000–12000)     | Drive PWR_SW for `ms` (default 6000) — hard power-off. |

## Response envelope

Device → relay → phone, addressed by `id`:

```json
{ "v": 1, "id": "<command id>", "ok": true,  "res": { ... } }
{ "v": 1, "id": "<command id>", "ok": false, "err": "replay|sig|stale|unknown_act|busy|usb_down|..." }
```

Response integrity rides on the device↔relay TLS + `deviceToken` (responses
are not signed in v1; signing them is a v2 candidate).

## Transport

### Device ↔ relay
- `wss://<relay>/v1/device/<deviceId>` with header
  `Authorization: Bearer <deviceToken>`.
- Device sends `{"hello": {"fw": "x.y.z"}}` on connect; relay pushes command
  envelopes as text frames; device pushes response envelopes.
- Keepalive is application-layer (Workers cannot emit RFC 6455 ping frames):
  the relay sends `{"v":1,"ping":<unix seconds>}` every 25 s — the device MUST
  ignore any frame that is not a command envelope (no `id`/`act`) and may treat
  it as liveness evidence; a device→relay text frame `ping` is answered `pong`.
  Device reconnects with exponential backoff (1 s → 60 s cap, ±20 % jitter).

### Phone ↔ relay
- `POST https://<relay>/v1/send/<deviceId>` with
  `Authorization: Bearer <deviceToken>`, body = command envelope.
  Relay forwards to the device if connected and returns the device's response
  (long-poll up to 10 s), else `504 {"err":"device_offline"}`.
- `GET /v1/presence/<deviceId>` (same auth) → `{"online": true, "since": ts}`
  (`since` = unix seconds of the last online/offline transition, `null` if the
  device has never connected).

The relay validates only: bearer token match, body ≤ 4 KiB, well-formed JSON,
`dev` matches path. It never inspects `sig` and stores nothing but the token
hash and presence.

## Pairing (trust on first use)

1. Fresh device (or BOOT held 5 s) starts SoftAP `remote-wake-<deviceId4>`
   (WPA2, password printed on serial/QR) and serves `http://192.168.4.1`.
2. Phone joins AP, opens the setup page, which collects: home Wi-Fi
   credentials, relay URL, and POSTs the phone's Ed25519 public key →
   `/pair {"pubkey": "<b64url>", "name": "Alex's phone"}`.
3. Device replies `{"deviceId": ..., "deviceToken": ..., "relayUrl": ...}`,
   which the PWA stores locally; device stores pubkey in slot `p1`
   (next free slot for subsequent pairings), then reboots into normal mode.
4. Pairing endpoint is ONLY available in setup mode — never on the home
   network, never via the relay.
